## 4. WebSocket por sub-protocolo

- [x] 4.1 Backend (`backend/src/api/mod.rs`, `ws_handler`; `backend/src/api/auth/session.rs`): aceitar o token de sessão também via `Sec-WebSocket-Protocol`, com a mesma validação (`hash_token` + lookup) já usada para cookie/header, como terceira alternativa (ver `openspec/changes/desktop-electron-shell/specs/auth/session-tokens/spec.md`). **Não usar o `.protocols(...)` do `WebSocketUpgrade` do Axum** — essa API serve para declarar um menu fixo de nomes de protocolo conhecidos em tempo de rota, não para aceitar um valor arbitrário (o token, diferente por sessão) como dado; ler o header `Sec-WebSocket-Protocol` directamente de `parts.headers`, mesmo padrão já usado para `Authorization`. **Corrigido durante a implementação**: ao contrário do que a RFC 6455, isolada, permitiria, o Chromium recusa o handshake quando o pedido oferece um sub-protocolo e a resposta 101 não selecciona nenhum — a resposta tem de ecoar um dos nomes oferecidos (o primeiro, por convenção) para a ligação abrir. Esse eco é só o que o protocolo exige para a ligação estabelecer; não participa na escolha da sessão, que continua cookie → header → sub-protocolo. Ver `design.md` Decisão 2 para o registo completo. Verificar com um teste de contrato (extensão de `backend/tests/contract/auth_session.rs`, mesmo padrão das tarefas de `native-client-auth`) que cobre: ligação autenticada só por sub-protocolo, logout a invalidar esse uso, e que cookie/header continuam a funcionar exactamente como antes (regressão).

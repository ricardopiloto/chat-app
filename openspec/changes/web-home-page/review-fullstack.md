## 2. Desenvolvimento do frontend
Veredito: Atenção
- **`npm run verify:tokens` citado em tasks.md 2.2/6.1 não existe hoje como script.** Concordo com o Arquiteto que `verify-tokens.mjs` (arquivo) não cobre `home.html`, mas fui verificar o `package.json` (`frontend/package.json:8-40`) e constatei um problema anterior a esse: **não há entrada `"verify:tokens"` nos `scripts`** — o arquivo `frontend/scripts/verify-tokens.mjs` existe no disco, mas não está ligado a nenhum comando `npm run`. O mesmo vale para `verify-theme.mjs`. Isso é uma lacuna pré-existente do repositório (outras changes, como `parley-server-standalone/tasks.md:17,51` e `instance-settings/tasks.md:56`, também citam `npm run verify:tokens` como se existisse), não introduzida por esta change, mas `web-home-page` a herda nas tarefas 2.2 e 6.1: quem implementar vai digitar `npm run verify:tokens` e receber `Missing script: "verify:tokens"`, não um "passou"/"falhou" real. A tarefa deveria ou trocar para `node scripts/verify-tokens.mjs` diretamente, ou (melhor, já que outras changes dependem do mesmo nome) acrescentar a entrada no `package.json` como parte da tarefa 2.2.
- **Padrão de script TS exige decisão explícita para `homeMode()`/`verify-marketing-home.mjs`.** `frontend/package.json` mostra um padrão claro: scripts que importam módulos `.ts` do app usam `node --experimental-strip-types scripts/verify-X.mjs` (`verify:entry-screens`, `verify:instance-setup`, `verify:email-registration`, `verify:email-reset`, `verify:updates`, `verify:legacy-cleanup`; ver `verify-entry-screens.mjs:4`, que importa `../src/auth/entryScreen.ts` via `await import(...)`). A tarefa 1.2 não menciona esse detalhe; se `homeMode()` for escrito em `.ts` (caminho natural, ao lado de `entryScreen.ts`), o novo script `verify-marketing-home.mjs` e sua entrada em `package.json` precisam seguir o mesmo padrão (`--experimental-strip-types`), senão o `import` falha silenciosamente com outro erro de sintaxe. Não é um bloqueante, só uma armadilha concreta de implementação que vale citar na própria tarefa.
- **`verify-i18n-keys.mjs` tem a mesma lista fixa de catálogos que `verify-brand`/`verify-entry-screens`**, e o Arquiteto não cobriu esse script especificamente. `scripts/verify-i18n-keys.mjs:15-22` monta um arquivo de entrada temporário com `import`s hardcoded de `en`, `pt-BR`, `legacy/*`, `chat.*`, `mgmt.*`, `settings.*`, `voice.*` e os funde manualmente nessa mesma lista. Isso tem duas implicações diretas para D10:
  - Se `marketing.*` ficar em `pt-BR.ts`/`en.ts` (D10 como está escrito), `verify-i18n-keys` funciona sem mudança — mais um motivo a favor de manter D10 como está, e não só o argumento de volume de texto que o Arquiteto levantou.
  - Se a recomendação do Arquiteto for seguida (criar `marketing.pt-BR.ts`/`marketing.en.ts` dedicados, no padrão `mgmt.*`/`voice.*`), **tanto `frontend/src/i18n/index.ts:2-25` quanto `scripts/verify-i18n-keys.mjs:15-22` precisam de edição manual** para importar e `merge()` os dois novos arquivos — exatamente o mesmo tipo de lista fixa que já é um ponto de atenção em `verify-brand.mjs`/`verify-entry-screens.mjs`. Se o Arquiteto mantiver essa recomendação, a tarefa 2.1 deveria listar essas duas edições explicitamente, não só "escrever os textos em `pt-BR.ts`/`en.ts`" (que hoje aponta para os catálogos centrais, não para um par dedicado).
- `verify-i18n.mjs` (motor de i18n, troca de idioma, persistência) não depende de nenhuma lista de catálogos e não precisa de mudança — confirmado lendo o arquivo inteiro; cobre `t()`/`setLocale()` de forma agnóstica ao conteúdo.
- `frontend/src/components/ui/` (`Button.tsx`, `Badge` via `index.tsx`, `Logo.tsx`, `Display.tsx`, `Form.tsx`, `Overlay.tsx`, `Icon.tsx`) já é exatamente o kit que `WebPublicHome.tsx` usa hoje (`Button`, `Badge`, `Logo`) — D7 é implementável sem componente novo, na prática, não só na teoria do design.md. `frontend/src/entry.css` hoje só tem `.entry-control` e uma regra de `scroll-behavior`/`outline` para `.public-home`; `marketing.css` pode seguir o mesmo padrão de arquivo pequeno e específico de página, sem necessidade de tocar `tokens.css` nem `components/ui.css` — e `verify-entry-screens.mjs:35-40` ativamente bloqueia qualquer diff nesses arquivos protegidos (`tokens.css`, `tailwind.config.ts`, `ui.css`, `components/ui`), então uma tentativa de "ajustar um pouco o token" durante a implementação de `MarketingHome` quebraria essa guarda — é um bom freio, mas quem implementar deve saber que existe antes de tentar.
- O stub de `MarketingHome` que o Arquiteto recomendou para a tarefa 1.2 (seção 5, item final) é real: hoje não há `frontend/src/pages/MarketingHome.tsx` nenhum, e a tarefa 1.2 pede a `Match` escolhendo entre `MarketingHome`/`WebPublicHome` antes da tarefa 2.2 criar o componente de verdade. Confirmo esse achado e endosso a recomendação.
